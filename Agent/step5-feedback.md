# STEP 5. 냉철한 피드백과 반영

기준: `step1-design.md` ~ `step4-flow-ui.md`, 가이드라인 STEP 5.
상태: 피드백 확정본. 아래 "반영"은 설계 문서에 적용했거나 STEP 6 구현에 반드시 포함할 항목이다.

## 관점 1 — 공장 작업자(신입·경력 페르소나)

바쁜 현장에서 실제로 쓸까? 더 편한 방법은 없을까?

- 알림 하나하나에 "AI 점검 안내"를 열어 질문 버튼을 누르는 흐름은, 급할 때는 그냥 상세 패널의 숫자만 보고 끝낼 수 있다. 에이전트를 거쳐야 할 이유가 약하면 안 쓴다.
- 추천 질문 3개가 분리돼 있어 ①②③을 각각 눌러야 전체 그림이 나온다. 현장에서는 "그래서 지금 뭐부터 해?"가 한 번에 나와야 한다.
- 응답이 느리면(도구 여러 번 + LLM) 작업자는 기다리지 않는다.

> **가장 먼저 고칠 것:** "한 번에 다 알려줘" 버튼 하나를 추가한다. 누르면 어떤 이상 → 우선순위·근거 → 첫 점검 행동·보고 조건까지 **한 답변**에 요약으로 나오게 한다(내부적으로 도구 ①②③을 순서대로 호출). 개별 버튼은 더 깊이 보고 싶을 때만 쓴다.

## 관점 2 — 공장 관리자/임원

에이전트 결과를 믿고 의사결정할 수 있는가?

- 모든 수치에 "데모 데이터" 배지가 붙는데, 그러면 "이걸로 결정해도 되나?"라는 의심이 든다. 데모임을 숨기면 안 되지만, **무엇이 확인된 사실이고 무엇이 미확인인지** 경계가 더 분명해야 신뢰가 생긴다.
- `toolTrace`가 개발자용으로만 보이면 관리자는 "AI가 지어낸 것 아니냐"를 확인할 길이 없다.
- 우선순위 정책(과전류·불균형=high 등)이 "데모 기준"이라는데, 근거가 화면에 안 보이면 설득력이 떨어진다.

> **가장 먼저 고칠 것:** 답변에 **"확인된 값 / 미확인·보류 항목"을 항상 분리**해 표시하고, 각 수치 옆에 출처(규칙 ID·demoOnly)를 붙인다. 관리자용으로 `toolTrace`를 "근거 보기"로 사람이 읽을 수 있게 노출한다(어떤 도구가 어떤 사례를 조회했는지).

## 관점 3 — AI 서비스 기획자

이게 챗봇이 아니라 에이전트인가? 도구·규칙 설계가 적절한가?

- 도구 호출 순서가 흐름도에 고정돼 있어서, 자칫 "정해진 순서대로 실행하는 자동화"처럼 보일 수 있다. 에이전트라면 **요청에 따라 LLM이 도구를 스스로 골라야** 한다(가이드라인 셀프체크 1번).
- "한 번에 다 알려줘"를 서버가 ①②③ 고정 호출로 처리하면 그 요청만큼은 자동화에 가까워진다. 에이전트성과 속도의 트레이드오프를 명시해야 한다.
- 대화 맥락 재사용(이미 조회한 사례 재질문)이 설계엔 있지만, 구현에서 빠지기 쉽다.

> **가장 먼저 고칠 것:** 흐름도는 "예상 흐름"일 뿐 **실제 도구 선택은 LLM이 한다**는 점을 구현·발표에서 못박는다. "한 번에 다 알려줘"도 가능하면 LLM이 필요한 도구를 선택하게 하고, 안정성을 위해 고정 순서를 쓰는 경우 그 사실을 toolTrace로 투명하게 남긴다.

## 설계 반영 (변경점)

| # | 무엇을 | 왜 | 어디에 반영 |
| --- | --- | --- | --- |
| 1 | 추천 질문에 **"한 번에 다 알려줘(종합 점검)"** 버튼 추가 (총 4버튼) | 바쁜 작업자가 한 번에 전체 판단을 얻게 | step4 화면 설계 + STEP 6-2 ④ 구현 |
| 2 | 답변에 **"확인된 값 / 미확인·보류" 분리** 블록 고정 | 관리자 신뢰, 안전(미확인을 확인처럼 안 보이게) | step3 프롬프트 응답형식 + step4 메시지 영역 |
| 3 | 수치 옆 **출처(규칙 ID·demoOnly)** 상시 표시 | 데모/실데이터 혼동 방지 | step3 규칙 + step4 상세 영역 |
| 4 | `toolTrace`를 **"근거 보기"로 사람이 읽게** 노출 | 에이전트가 실제 도구를 썼다는 증거 | step4 API 계약 + 화면 |
| 5 | **"도구 선택은 LLM이 한다"** 명시, 고정 순서 사용 시 toolTrace에 표기 | 챗봇/자동화와 구분(에이전트성) | step4 흐름 주석 + STEP 7 발표 |
| 6 | 응답 지연 대비: **로딩 상태 + 호출 한도/타임아웃** | 안 기다리는 사용자 대응 | step4 상태 + STEP 6-2 ③ 서버 |

## 반영 메모

- 변경점 1·2는 아래에서 step3/step4 문서에 직접 반영한다.
- 변경점 4·5·6은 이미 step4 API 계약(`toolTrace`)과 서버 설계에 뼈대가 있으므로 STEP 6 구현 시 "사람이 읽는 근거 보기"와 "한도/타임아웃"을 반드시 포함한다.
- 핵심 트레이드오프: "한 번에 다 알려줘"는 편의 vs 에이전트성. LLM 자율 선택을 우선하되, 데모 안정성을 위해 서버가 보조 순서를 둘 수 있고 그 사실을 숨기지 않는다.
