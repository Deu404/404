# STEP 4. 대화 흐름·화면 설계하기

기준: `step1-design.md`, `step2-tools.md`, `step3-prompt.md`, 가이드라인 STEP 4.
스택: B안(React 대시보드 `404-main` + TypeScript 백엔드 서버). 가이드라인의 Streamlit 예시 기능은 React 등가물로 대체한다.
상태: 설계 확정본. 실제 컴포넌트 구현은 STEP 6-2 ④에서 한다.

## 가이드라인 Streamlit 기능 → React 대응

| 가이드라인(Streamlit) | 이 프로젝트(React) |
| --- | --- |
| `st.chat_input` | 채팅 입력창 컴포넌트 (textarea + 전송 버튼) |
| `st.chat_message` | 메시지 말풍선 컴포넌트 (user / assistant 구분) |
| `st.button` (추천 질문) | 추천 질문 버튼 3개 |
| `st.download_button` | (1차 범위 밖) 필요 시 보고 초안 복사 버튼으로 대체 |
| `st.session_state` | React state + 서버가 관리하는 `conversationId` |

대화 기록은 가이드라인대로 유지한다. 브라우저 state에 메시지를 쌓고, 서버는 `conversationId`로 같은 대화를 이어간다. API 키는 서버에만 두므로 브라우저에서 OpenAI를 직접 호출하지 않는다.

## 1. 대화 흐름 (대표 요청 3개)

세 요청 모두 "현재 선택된 사례(caseId)"를 맥락으로 전달한다. 사례가 없으면 에이전트가 되묻는다.

### 대표 요청 ① "선택한 설비의 이상 사례를 확인해서 어떤 이상인지 알려줘."

```
사용자 요청(+caseId)
  → [도구] get_anomaly_case(caseId)
       ├ not_found → "해당 사례를 찾을 수 없다" (분기 A)
       └ ok/partial
            → [도구] classify_anomaly(caseId)
                 ├ 모두 insufficient_data → "측정값 부족, 판정 보류 + 누락 항목" (분기 B)
                 ├ 모두 within_threshold → "이 규칙에서 이상 조건 미확인" (분기 C)
                 └ 하나 이상 matched → 확인된 유형 요약
  → 최종 답변: 3줄 요약(어떤 이상/근거/첫 행동) + 상세(값·단위·시각·규칙)
```

### 대표 요청 ② "이 이상을 어느 우선순위로 확인해야 하고, 판단 근거는 뭐야?"

```
사용자 요청(+caseId)
  → (①에서 이미 조회했으면 맥락 재사용, 아니면) get_anomaly_case
  → [도구] evaluate_priority(caseId)
       ├ priorities 있음 → 유형별 우선순위(high→medium 순) + 근거
       ├ unassessedTypes 있음 → 해당 유형은 "판단 불가"로 분리 표시 (분기 D)
       └ 모두 미평가 → "근거 부족, 우선순위 판단 보류"
  → 최종 답변: 우선순위 + 근거(값·임계치·규칙ID). 복합 이상은 유형별로 나열
```

### 대표 요청 ③ "이 상황에서는 무엇부터 점검하고 어떤 조건에서 보고해야 해?"

```
사용자 요청(+caseId)
  → (맥락 없으면) get_anomaly_case → classify_anomaly
  → 확인된(matched) 유형마다 [도구] get_inspection_guide(alertType)
       ├ 가이드 있음 → 초기 대응 + 점검 순서 + 보고 조건
       └ not_found → "등록된 가이드 없음, 담당자 확인 안내" (분기 E, 절차 생성 금지)
  → 최종 답변: 점검 순서(번호) + 보고 조건 + 출처(demoOnly)
```

## 2. 결과에 따라 달라지는 분기 (요약)

| 분기 | 조건 | 에이전트 행동 |
| --- | --- | --- |
| A | 사례 not_found | 다른 사례로 대체하지 않고 대상 재확인 요청 |
| B | 측정값 전부 누락 | 판정 보류, 누락 항목 명시 |
| C | 모든 유형 within_threshold | "이 규칙에서 이상 미확인", 안전 보증은 하지 않음 |
| D | 일부 유형 미평가 | 평가된 유형과 미평가 유형을 구분 표시 |
| E | 가이드 없음 | 점검 절차 생성 금지, 미등록 안내 + 담당자 확인 |

복합 이상(여러 유형 matched)은 유형별 우선순위·근거를 유지하고 유형마다 가이드를 각각 조회한다. 같은 우선순위에 임의 순위를 만들지 않는다.

## 3. 화면 설계 (React 대시보드 통합)

### 위치 결정

기존 `이상 알림`(`/alerts`) 화면에 자연스럽게 붙인다. 그 화면은 이미 알림을 선택하면 상세·판단 근거·"관련 점검 가이드" 링크를 보여주므로, 에이전트는 **선택된 알림을 사례(caseId)로 받는 "AI 점검 안내" 패널**로 들어간다. 메뉴마다 별도 에이전트를 만들지 않는다(설계 원칙).

- 1차 안: `/alerts`의 선택 알림 상세 패널 하단에 "AI 점검 안내" 버튼 → 누르면 우측/하단에 에이전트 패널(또는 모달) 열림.
- 선택한 알림이 바뀌면 에이전트에 새 caseId를 전달하고, 새 대화인지 이어지는 대화인지 구분한다.

### 패널 레이아웃 (위에서 아래로)

```
┌───────────────────────────────────────────┐
│  AI 점검 안내            [데모 데이터] 배지   │  ← 헤더: 대상 설비·사례ID, demoOnly 표시
├───────────────────────────────────────────┤
│  추천 질문                                   │  ← 타이핑 없이 쓰는 버튼 4개
│  [⭐한 번에 다 알려줘]                         │     = 종합 점검(STEP 5 반영)
│  [어떤 이상인지] [우선순위·근거] [점검·보고]    │     = 대표 요청 ①②③
├───────────────────────────────────────────┤
│                                           │
│   (assistant) 3줄 요약 ...                 │  ← 메시지 영역(st.chat_message 대응)
│       ▸ 상세 보기 (펼침: 근거·점검 순서)      │     요약 먼저, 상세는 접힘
│   (user) 사용자가 입력한 질문                 │
│                                           │
│   [로딩 중...] / [실패: 다시 시도]            │  ← 상태 표시
├───────────────────────────────────────────┤
│  [ 메시지 입력창......................][전송] │  ← st.chat_input 대응
└───────────────────────────────────────────┘
```

### 각 영역 상세

- **헤더**: 대상 설비명·사례 ID, `demoOnly`면 "데모 데이터" 배지. 기존 화면의 `mock-badge` 스타일 재사용.
- **추천 질문 버튼 4개**: 맨 위 "⭐한 번에 다 알려줘(종합 점검)" + 대표 요청 ①②③(어떤 이상/우선순위·근거/점검·보고). "한 번에 다 알려줘"는 어떤 이상 → 우선순위·근거 → 첫 점검 행동·보고 조건까지 한 답변에 요약으로 제공한다(STEP 5 관점1 반영). 바쁜 작업자가 타이핑 없이 누르기만 하면 됨. 버튼을 누르면 해당 문장이 입력창에 들어가 바로 전송.
- **메시지 영역**: user/assistant 말풍선. assistant 답변은 **3줄 요약을 먼저** 보여주고, "상세 보기"를 펼치면 수치 근거·점검 순서·보고 조건·부족 정보 표시(신입/경력 모두 대응). 복합 이상은 유형별 블록.
- **확인된 값 / 미확인·보류 분리**(STEP 5 관점2 반영): 상세 영역은 "확인된 값"(도구가 돌려준 값·단위·규칙 ID·demoOnly)과 "미확인·보류 항목"(missingFields, unassessedTypes)을 **항상 두 블록으로 나눠** 표시한다. 미확인을 확인된 사실처럼 보이지 않게 한다.
- **근거 보기**(STEP 5 관점2·3 반영): `toolTrace`를 사람이 읽을 수 있게 "근거 보기"로 노출한다. 어떤 도구가 어떤 사례를 조회했는지 보여 에이전트가 실제 도구를 썼음을 확인시킨다.
- **상태 표시**: 로딩(스피너), 실패(에러 메시지 + 다시 시도), 데이터 부족(누락 항목 안내)을 서버 `status`에 따라 구분. API 오류를 성공 분석처럼 보이지 않게 한다.
- **입력창**: 자유 질문. 전송 시 현재 caseId와 conversationId를 함께 서버로 보냄.

### 타이핑 없이 쓰는 흐름 (바쁜 사용자)

알림 선택 → "AI 점검 안내" 열기 → 추천 질문 버튼 ① 클릭 → 3줄 요약 확인 → 필요하면 버튼 ②③ 연속 클릭. 키보드 입력 없이 대표 흐름 완주 가능.

## 4. 서버 연결 계약 (화면 ↔ 서버)

```
POST /api/agent
요청: { message, caseId, conversationId? }
응답: {
  status, conversationId,
  reply: { summary, detail },        // summary=3줄 요약, detail=상세
  evidence,                          // 도구가 확인한 값·단위·규칙 근거
  steps, reportConditions,           // 가이드 기반(있을 때)
  missingFields,
  dataSource, demoOnly,
  toolTrace                          // 호출한 도구 이름·성공여부(키·원본 제외)
}
```

- 서버가 대화 기록을 보관하고 새 대화/사례 변경을 구분한다.
- `toolTrace`로 "실제 도구가 호출됐다"는 증거를 화면·발표에서 보여줄 수 있다(가이드라인 셀프체크 2·3번).

## STEP 4 셀프체크

- 대표 요청 3개 흐름(요청→도구 순서→최종 답변): 작성함.
- 분기 표시(결과에 따라 행동 변화): A~E로 명시.
- 채팅창·추천 버튼·결과 표시 위치: 레이아웃으로 구체화.
- 타이핑 없이 쓰는 방법: 추천 버튼 3개로 완주 흐름 제시.
- 대시보드 한 탭(패널)으로 통합: `/alerts` 선택 알림 패널에 연결, 별도 에이전트 안 만듦.
- Streamlit 기본 기능 범위: React 등가물로 1:1 매핑.
