# STEP 1. 한 장에 설계하기

기준: 팀 역할 분담과 1차 멘토링 에이전트 제작 가이드라인
상태: 설계 초안. 함수·GPT 연결·화면 연결은 아직 구현하지 않았다.

## 핵심 방향

**설비 이상 대응 에이전트 하나를 만든다.** 가상 이상 사례를 조회하고, 사전 규칙으로 이상 유형과 우선순위를 판단한 뒤 해당 상황의 점검 가이드를 제공한다. 결과는 화면 담당자가 기존 대시보드에 연결할 수 있는 형식으로 전달한다.

| 항목 | PlantEye 에이전트 설계 |
| --- | --- |
| **누가 / 언제** | **공장 신입 및 경력 작업자 모두**가 설비의 이상 징후를 확인하고 유형·우선순위·점검 방법을 판단해야 할 때 사용한다. 첫 시연에서는 가상 이상 사례를 선택하거나 해당 사례의 설비를 지정해 요청한다. 신입은 쉬운 설명과 확인 순서를, 경력자는 핵심 수치와 판단 근거를 확인한다. 화면에서 실행하는 위치는 화면 담당자와 협의한다. |
| **목표** | 입력된 가상 이상 사례에 대해 **이상 유형·우선순위·판단 근거·점검 순서·보고 조건**을 제공하여 작업자가 다음 행동을 결정하도록 돕는다. 이미 완성된 알람 문구를 다시 설명하는 데 그치지 않고 입력값에 판단 규칙을 적용한 결과를 제공한다. |
| **대표 요청** | ① “선택한 설비의 이상 사례를 확인해서 어떤 이상인지 알려줘.” ② “이 이상을 어느 우선순위로 확인해야 하고, 판단 근거는 뭐야?” ③ “이 상황에서는 무엇부터 점검하고 어떤 조건에서 담당자에게 보고해야 해?” 두 사용자 모두 사용할 수 있다. 대상이 없거나 여러 사례 중 어느 것을 뜻하는지 모호하면 확인한다. |
| **도구 목록** | `get_anomaly_case(사례 ID)` → 설비 ID·측정 시각·측정값·단위·비교 기준·제공된 탐지 결과·출처·누락 항목. 입력에 유형과 우선순위가 미리 정해져 있다고 가정하지 않는다.<br>`classify_anomaly(사례 ID)` → 규칙에 따른 이상 유형 목록·적용 규칙·측정값과 기준값·판단 가능 여부. 복합 이상·기준 내·데이터 부족을 구분한다.<br>`evaluate_priority(사례 ID)` → 유형별 우선순위·판단 근거 또는 판단 불가. 함수가 원본 사례와 규칙을 직접 확인한다.<br>`get_inspection_guide(이상 유형)` → 등록된 가이드의 점검 순서·초기 대응·보고 조건·출처. 상세 입출력은 STEP 2에서 구체화한다. |
| **규칙** | 유형 분류·계산·우선순위 판단은 사전 규칙을 적용하는 함수가 수행한다. AI는 필요한 도구를 선택하고 결과에 따라 추가 조회 또는 안내를 결정한다. **경력에 따라 사실·우선순위·보고 조건을 바꾸지 않는다.** 수치는 도구 결과만 사용하고 단위·측정 시각·출처를 표시한다. 고장 원인과 미래 고장을 단정하지 않는다. 필요한 측정값이나 기준이 없으면 해당 판단을 보류하고 누락 항목을 안내하되 확인 가능한 결과는 구분해서 제공한다. 점검 안내는 사전에 등록된 가이드에 근거하며, 가이드에 없는 조치는 임의로 제안하지 않는다. 가이드가 없으면 담당자 확인을 안내한다. 가상 시연 데이터와 실제 데이터 분석 결과는 출처를 구분해 표시한다. 과거 분석을 현재 실시간 이상처럼 표현하지 않는다. |
| **화면** | 사용자님은 에이전트 코드와 결과 형식을 준비하고, 화면 담당자는 기존 대시보드에 연결한다. 결과에는 이상 유형·우선순위·근거·점검 순서·보고 조건·출처·부족한 정보를 포함한다. 공통 요약에는 이상 내용·우선순위·첫 확인 행동을, 상세 영역에는 쉬운 설명·수치 근거·점검 항목을 표시하는 구성을 제안한다. 실행 버튼·추천 요청·질문 입력창의 필요 여부와 위치는 화면 담당자와 합의한다. 메뉴마다 별도 에이전트를 만들지 않는다. |
| **성공 기준** | 대표 요청 3개가 실제 도구 호출로 처리되고 유형·우선순위·수치·점검 항목이 함수 결과와 일치한다. 이상 유형에 맞는 가이드를 조회하고 복합 이상·기준 내·측정 누락·가이드 없음에 따라 결과가 달라진다. AI가 요청에 따라 도구를 선택하고 결과를 받아 추가 호출 또는 최종 답변을 결정하는 실행 기록을 확인한다. 화면 담당자에게 샘플 JSON·필드 설명·실행 연결 방법을 제공한다. 화면 연결 후 결과 표시 시점부터 신입은 30초 안에 첫 확인 행동과 보고 조건을, 경력자는 30초 안에 우선순위 근거와 다음 행동을 설명하는 것을 목표로 각각 테스트한다. API 응답 시간은 별도 측정 후 목표를 정한다. |

## 입력과 출력의 경계

- 초기 입력은 시연용 가상 이상 사례다. 제공된 설비 데이터의 필드와 단위를 참고하되 가상으로 변경한 값과 시나리오는 표시한다.
- a팀원의 전기요금·탄소 예측 결과는 이상 탐지 결과와 별개다. 예측 파일만으로 과전류나 설비 고장을 추정하지 않는다.
- 실제 이상 탐지 결과가 제공되면 같은 입력 경계에 연결하는 방식을 검토한다. 실제 이상 탐지 모델 학습까지 사용자님 역할에 포함된 것으로 가정하지 않는다.
- 유형 후보는 기존 화면의 과전류·역률 저하·전력 소비 증가·상간 전류 불균형이다. 필요한 값과 근거 있는 기준이 있는 유형부터 구현한다.
- 현재 코드의 임계치와 가이드는 데모 자료다. 실제 설비 기준이나 현장 표준으로 확정된 것처럼 표시하지 않는다.
- 원본 CSV 전체를 GPT에 보내지 않는다. 도구가 필요한 사례와 계산 결과만 반환한다.

## 요청과 결과에 따라 달라지는 동작

“선택한 사례를 분석하고 대응을 알려줘” → 사례 조회 → 분류·우선순위 함수 호출 → 확인된 유형의 가이드 조회 → 결과 반환.

- 복합 이상: 유형별 우선순위와 근거를 유지하고 필요한 가이드를 각각 조회한다. 같은 우선순위는 임의로 순위를 만들지 않는다.
- 기준 내: 해당 규칙에서 이상 조건이 확인되지 않았다고 설명한다. 정상이라는 이유로 실제 안전을 보증하지 않는다.
- 측정값 부족: 판정 가능한 항목과 보류한 항목을 구분한다.
- 가이드 없음: 점검 절차를 생성하지 않고 미등록 상태를 안내한다.
- 유형만 묻는 요청과 대응까지 묻는 요청에서 필요한 도구 선택이 달라진다. 이미 확인한 정보는 대화 맥락으로 재사용하되 사례가 바뀌면 새 사례를 조회한다.

핵심은 **요청에 필요한 정보를 조회하고, 판단 결과에 따라 다음 도구 호출과 최종 안내를 구성하는 실행 루프**다. 이 동작 없이 고정 순서만 실행한다면 규칙 기반 자동화에 머무르므로 구현 시 확인한다.

## 이번 범위

포함: 가상 사례 조회, 규칙 기반 유형·우선순위 판단, GPT의 도구 선택과 설명, 가이드 조회, 구조화된 결과 전달.

후속 범위: 요금·탄소 예측 설명, 교대 인수인계, 보고서 작성·전송, 복잡한 대화형 점검, 기간별 반복 집계·알람 통합. 첫 구현의 필수 기능으로 두지 않는다.

## 팀원에게 공유·확인할 부분

- **화면 담당자:** 에이전트 결과와 기존 화면의 데모 판단 중 어느 결과를 기준으로 표시할지 합의한다. 반환 결과가 프런트 규칙에서 다시 계산되어 바뀌지 않도록 연결 경계를 정한다. 사례·설비 ID 매핑, 결과 필드, 실행 위치, JSON 파일/API 방식, 오류·부족 정보 표시도 협의한다.
- **데이터 담당·팀 전체:** 가상 사례 준비 주체와 실제 이상 탐지 결과 제공 여부, 단위·비교 기준, 임계치·우선순위 규칙의 근거, 가이드의 데모/검토 상태를 확인한다.
- **팀 전체:** 두 페르소나를 모두 주 사용자로 두고 첫 범위를 설비 이상 대응에 한정한다는 점을 공유한다.
